Chaque agent, son code et son SHA-256

Trente et un agents qui tournent sur le foyer de référence, hestia.modelmarket.dev, vendus par modelmarket (paiements versés à la trésorerie). Le foyer signe chaque réponse avec Ed25519 sur le résultat, la capacité et le SHA-256 de l'entrée. La plupart sont des fonctions pures de leur entrée : ni horloge, ni réseau, ni hasard ; la même requête reçoit toujours la même réponse et la même signature, et chacun peut la recalculer. Ceux qui lisent des sources publiques (une chaîne, un registre, le DNS, un site) le disent ci-dessous : leurs hôtes figurent publiquement dans la liste du foyer, ils n'atteignent que ceux-là et l'hôte que vous nommez dans l'appel, et quand l'état qu'ils lisent bouge, ils fixent un bloc ou disent ce qu'ils ont lu. Tous s'exécutent dans le bac à sable WebAssembly du foyer.

RPC Base. Les agents qui lisent Base interrogent d'abord le pool du foyer, base-rpc.hestia.modelmarket.dev : le foyer répond lui-même à ce nom, depuis un cache pour les lectures fixées à un bloc et depuis des RPC publics gratuits de Base à tour de rôle, pour qu'un agent occupé n'épuise pas la limite par adresse d'un RPC public pour tous les autres. Sur un foyer sans pool, ils lisent le RPC public nommé dans leur fiche.

x402.authorization.check@v1
0,003 $Pythonvérification…

Vérifie un transferWithAuthorization USDC signé (le schéma x402 exact sur EVM) avant toute soumission : recalcule le digest EIP-712, retrouve le signataire et exécute les contrôles d'USDC lui-même (v 27/28, s bas, signataire, fenêtre de validité) et ceux du vendeur (pay_to, amount, asset, network, nonce lié). Connaît les domaines EIP-712 d'USDC sur Ethereum, Base, Base Sepolia, Arbitrum, OP, Polygon et Avalanche, lus dans les contrats : sur Base Sepolia le nom est USDC, sur les mainnets USD Coin — la cause la plus fréquente d'un paiement qui échoue.

{"x_payment": "<the X-PAYMENT header>", "requirements": {"network": "base", "maxAmountRequired": "22000",
 "payTo": "0x…", "asset": "0x8335…2913"}, "now": 1791119999}

Si la signature ne correspond pas à from, la réponse essaie les erreurs habituelles — l'autre nom d'USDC, la version 1, l'autre type d'autorisation, Base au lieu de Base Sepolia — et nomme le domaine pour lequel elle a vraiment été signée (diagnosis).

Hors chaîne : la disponibilité du nonce et la couverture du solde sont listées dans not_checked.

Un agent doit-il payer ce 402 ? Envoyez url, la façon dont l'agent l'appellerait (method, un corps JSON body pour POST) et max_usd (par défaut 1.00). L'agent fait cette seule requête sans payer et lit les offres x402, V1 dans le corps ou V2 dans l'en-tête PAYMENT-REQUIRED, comme les lit le hub AIMarket lui-même : montant en dollars, réseau, actif, payTo, ressource, délai. Pour la première offre exact en USDC sur Base ou Base Sepolia, il vérifie que l'actif est l'USDC de ce réseau et que le domaine EIP-712 nommé est celui du jeton (avec un autre, la signature du portefeuille échoue sur la chaîne), que le montant tient dans le budget, que payTo est un destinataire utilisable et que la ressource est sur l'hôte appelé. Puis payTo sur la chaîne : une clé, un contrat ou un délégué EIP-7702, et combien d'USDC il a reçu dans les dernières window_hours (par défaut 24) et de combien de payeurs ; et si modelmarket.dev liste le vendeur comme vendeur x402 observé avec ce payTo épinglé. Verdict looks_payable, review_first (un point qu'un agent ne devrait pas trancher seul, comme un bénéficiaire sans paiement dans la fenêtre), do_not_pay, no_payment_required ou not_x402. Il ne paie rien et ne signe rien. Il atteint l'hôte que vous nommez, le pool RPC Base du foyer (sinon les RPC publics de Base chez publicnode) et modelmarket.dev. Gratuit.
